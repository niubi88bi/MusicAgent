# MusicAgent 代码思路、作用与问题复盘

> 历史复盘日期：2026-09-09；这是当时的阶段快照，不代表公开副本的当前测试数量或可运行范围。
> 当时依据：项目计划、技术决策、内部工作记录、性能记录和当时的 90/90 离线回归；公开副本没有附带旧实验数据。
> 口径：只把已经实现并验证的能力写成完成项；规划中的 RAG、音频评审、记忆、安全、MCP 和公网部署不计入当前成品。

## 1. 先说结论

MusicAgent 当前是一个可运行的中文歌曲创作 MVP。用户输入主题后，系统先用 DeepSeek 完成需求理解，两种 persona 的作词 Agent 并行生成候选；独立匿名评审从主题、自然度、情绪、叙事意象和 Hook 五维评价，再与确定性规则组合选优。入选稿继续用纯规则质检检查十三辙押韵、段落结构和 Hook；未达标时，LangGraph 最多让入选作词 Agent 修改两次。文本完成后，用户可以单独触发本地 HeartMuLa 生成 30 秒试听。

当前最重要的工程思想不是“堆很多 Agent”，而是下面四点：

1. 用结构化状态和数据契约把 LLM 的不确定输出变成可校验的工程输入。
2. 把主观比较与确定性规则分层：评审 Agent 判断表达质量，规则负责押韵和结构下限，并把具体反馈送回作词 Agent 形成闭环。
3. 把便宜、较快的文本阶段与昂贵、较慢的 GPU 音频阶段解耦。
4. 对失败、重试、产物和任务状态留证据，避免只剩一个不可解释的最终结果。

## 2. 当前完成边界

### 已实现并有证据

- DeepSeek 统一调用封装：配置隔离、有限重试、JSON Object、结构化契约校验和脱敏遥测。
- 五个结构化文本角色：需求理解 Agent、押韵结构型作词 Agent、意象表达型作词 Agent、匿名主观评审 Agent、制作 Agent。
- LangGraph 工作流：输入校验 → 需求理解 → 双作词并行 → 匿名主观评审与组合选优 → 规则质检与条件回炉 → 制作。
- 歌词确定性质检：十三辙押韵、响亮辙小幅加权、段落结构、时长对应最低行数和 Hook 位置用于评分与回炉；D9 第一版另输出句长/停顿/平仄和主题关键词直接命中的影子报告。
- 有限回炉：最多三稿；到上限仍未通过时选规则分最高稿，并明确标记 `capped`。
- FastAPI Web 闭环：创建文本任务、轮询真实节点事件、查看歌词/各稿/质检/制作方案。
- 按需音频：文本完成后单独创建 30 秒 HeartMuLa 任务；独立子进程、单容量、失败保留文本、手动重试和受限文件接口。
- 终态历史：服务重启后可以重新读取严格校验的 `done/failed` 快照。
- 当前离线回归：90/90 通过。
- 真实证据：DeepSeek 双作词与匿名评审文本链路已运行；历史三例评审回放均一次成功，与一名人工评审选择一致 2/3；新主题完成“评审选优 → 规则回炉 → 制作”；受控缺陷检测和指定缺陷修复为 3/3；本地 Web 已成功生成并播放一首 30.08 秒 MP3。

### 部分完成或证据不足

- 自然主题试点有完整运行样本，但没有自然主题触发回炉，不能评价自然歌词回炉效果。
- 语义契约自动修复已有代码和离线测试；真实重跑时首稿直接合格，没有真实触发该重试分支。
- 响亮辙加权属于项目规则设计，没有人工听评证明它会提升听感。
- 三条人工盲评中，规则与人工胜者只一致 1/3；但只有一名评审者，而且两者判断依据不同，不能用此小样本估计规则的真实预测能力。
- 主观评审回放与人工选择一致 2/3；“车站离别”仍出现审美判断分歧，因此不能把小模型评审当作人工标准或质量准确率。
- D9 的节奏参考分与主题词面覆盖尚未经过人工可唱性/主题标注校准，只能作为解释性建议，不能写成歌词质量提升证据。
- 音频只验证了单个 30 秒 Web 样本，不能承诺稳定耗时、音质或并发能力。
- 当前音频模型实际接收歌词和 `tags`；`style_prompt`、BPM、音色和完整编曲说明没有被证明严格执行。

### 尚未实现

- D9.4 的节奏权重、阈值和人工校准；主题词面信号当前不进入总分。
- ChromaDB + bge-small-zh 的 RAG 检索。
- 音频质量评审和音频回炉。
- SQLite 长期记忆、安全层、MCP 服务和公网部署。
- 多主题、多评审者的人工 A/B 盲评和真实用户试用反馈。
- Web 音频模型常驻；当前每次按需试听都会启动新的 Python 子进程并重新加载模型。

## 3. 系统结构

### 3.1 应用层

- `frontend/index.html`：页面结构。
- `frontend/styles.css`：桌面优先的深色工作台样式。
- `frontend/app.js`：提交任务、轮询状态、切换歌词版本、展示质检问题、触发和播放试听。
- `app/main.py`：FastAPI 入口，同源提供 API 和前端静态文件。

这一层负责把“长任务”变成可观察的产品体验。HTTP 请求不等待完整创作或音频生成，而是立即返回任务 ID，前端再轮询任务状态。

### 3.2 编排层

- `agents/state.py`：定义 LangGraph 共享状态，包括主题、需求、歌词、分数、回炉历史、最佳版本和最终采用版本。
- `agents/graph.py`：定义节点、条件边、最多三稿限制，以及文本模式和音频模式两种结束路径。
- `agents/requirement_agent.py`：把自然语言主题转成结构化歌曲需求。
- `agents/lyricist_agent.py`：以结构型和意象型 persona 生成候选；回炉时接收上一版全文和对应反馈。
- `agents/critic_agent.py`：匿名比较两份歌词、计算五维主观分，并实现重大问题过滤、近分规则兜底与候选共同回炉反馈。
- `agents/producer_agent.py`：把需求和歌词转成制作提示词、标签、人声方向和编曲说明。

LangGraph 在这里不是为了“看起来像 Agent”，而是用来表达有状态、有条件分支、有循环上限的工作流。单纯函数串联也能完成初稿，但难以清晰表达质检不通过后的回炉和版本选择。

### 3.3 规则工具层

- `tools/lyrics_quality/parser.py`：解析 Verse、Chorus、Bridge、Hook 标签并保留原始行号。
- `tools/lyrics_quality/thirteen_rhymes.py`：把普通话韵母归入十三辙，并处理 `ui/iu/un/v` 等缩写和写法差异。
- `tools/lyrics_quality/rhyme_checker.py`：分析行尾字、韵母、辙口和段内押韵模式，输出可定位的问题。
- `tools/lyrics_quality/structure_checker.py`：检查必要段落、时长对应的最低行数，以及 Hook 是否原样位于副歌或 Hook 段。
- `tools/lyrics_quality/scorer.py`：汇总分数、给出通过结论，并压缩成作词 Agent 可消费的反馈。

规则总分公式为：

```text
总分 = 押韵分 × 70% + 结构分 × 30%
```

通过条件不是只看总分，还必须同时满足：

- 总分至少 75；
- 押韵分至少 70；
- 结构分至少 75；
- Hook 原样位于 Chorus 或 Hook 段。

押韵分由可识别覆盖率、段内一致性和最高 10 分的响亮辙加分组成。两行段按 AA 检查，四行段在主导辙、AABB、ABAB 中选择最贴合模式，其他段按主导辙检查。这个分数只衡量规则合规，不衡量主题贴合、自然度、可唱性和听感。

### 3.4 服务层

- `services/config.py`：集中读取 DeepSeek 和 HeartMuLa 配置，隐藏 API Key。
- `services/llm.py`：封装 DeepSeek 调用、重试、JSON 解析、业务契约修复和遥测。
- `services/task_store.py`：线程安全内存任务表，限制状态只能按合法生命周期变化。
- `services/workflow_runner.py`：一个文本执行线程加两个等待名额，执行文本图并更新真实节点事件。
- `services/workflow_artifacts.py`：原子写入任务快照，保存需求、歌词、制作方案和逐轮质检证据。
- `services/audio_runner.py`：管理单容量音频任务，启动受控子进程，记录状态和日志。
- `services/music_gen.py`：封装 HeartMuLa 的权重加载、GPU 串行锁、输入文件和输出 MP3 校验。

### 3.5 脚本与测试层

- `scripts/run_draft_pipeline.py`：单独验证主题到制作方案，并支持阶段恢复。
- `scripts/run_pipeline.py`：命令行运行完整 LangGraph + 音频链路，也能复用已有草稿跳过 LLM。
- `scripts/run_text_workflow_validation.py`：运行真实文本链路，明确跳过音频。
- `scripts/evaluate_quality_loop.py`：运行自然主题和受控缺陷评估，保存 Token、延迟、失败和匿名盲评材料。
- `scripts/replay_subjective_judge.py`：只读取历史双作词候选并回放主观评审，不重新作词或加载 GPU。
- `scripts/run_audio_task.py`：Web 音频子进程入口，只读取指定 Web 任务目录内的结构化产物。
- `tests/`：用替身 Agent、替身 LLM 和假 MP3 验证控制流与失败边界，不消耗 API 或 GPU。

## 4. 三条实际运行链路

### 4.1 Web 文本创作链路

```text
浏览器 POST /api/tasks
  → WorkflowRunner 检查容量并创建 pending 任务
  → 单线程 worker 将任务改为 running
  → 构建 text_only LangGraph
  → validate_input
  → requirement：主题转 SongRequirement
  → lyric_candidate × 2：两个 persona 并行生成并分别计算规则报告
  → subjective_judge：匿名五维评分与重大主题问题识别
      ├─ 双方都有重大主题问题且未重写过 → 两个 persona 各自带反馈共同重写一次
      └─ 其他情况 → 进入组合选优
  → lyricist_selection：主观明显胜出；近分时由规则结果决胜
  → quality：规则评分与条件路由
      ├─ 不通过且未到三稿 → 带上一稿和反馈回到 lyricist
      ├─ 通过 → producer
      └─ 三稿仍不通过 → 选历史最高分稿，标记 capped，再到 producer
  → 保存 requirement/candidates/subjective review/selection/lyrics/production/quality/history
  → 先落盘终态快照，再把内存任务发布为 done
  → 前端轮询并展示结果
```

重要语义：`done` 表示文本流程正常结束，不表示歌词规则一定通过。规则结论单独看 `quality_status=passed|capped`。

### 4.2 歌词回炉链路

初稿计为第 1 次，最多生成 3 稿。每轮保存标题、歌词、Hook、分项分数、完整问题、反馈和来源稿次。回炉不是让模型完全重写，而是把上一版全文与规则反馈一起传入，并要求保留未被指出需要修改的内容、主题和可用意象。

如果第三稿仍未通过，系统不会无限循环，也不会把失败伪装成成功，而是选择三稿中规则总分最高的版本继续制作，并设置 `quality_status=capped` 和 `selected_attempt`。

### 4.3 Web 按需音频链路

```text
浏览器 POST /api/tasks/{id}/audio
  → 只接受已完成且有最终采用稿的文本任务
  → AudioRunner 检查幂等和单任务容量
  → 保存 audio_task.json
  → 独立 Python 子进程运行 scripts.run_audio_task
  → 校验 source-dir 和 32 位任务 ID
  → 重新读取 lyric_draft.json 与 production_plan.json
  → HeartMuLa 接收歌词、tags 和固定 30 秒时长
  → 只有预期路径的非空 song.mp3 才发布 audio_url
  → GET /api/tasks/{id}/audio 通过受限接口返回 audio/mpeg
```

音频失败只把音频任务标记为失败，不会把已经完成的文本任务改坏。用户可以继续查看歌词和质检报告，并手动重试。

## 5. 关键状态和字段含义

- `pending`：任务已接收但尚未运行。
- `running`：worker 正在真实执行任务。
- `done`：对应任务流程完成。文本 `done` 不等于歌词规则通过。
- `failed`：任务执行或产物保存失败。
- `attempts`：歌词生成次数，包含初稿，最大为 3。
- `candidate_regeneration_count`：两个候选因双方重大主题问题而共同回炉的次数，最大为 1；不与入选后的 `attempts` 混算。
- `subjective_review`：最新一轮匿名五维评分、证据、问题和 A/B 映射。
- `candidate_selection.selection_basis`：本次由重大问题过滤、主观分差或近分规则兜底决定。
- `selected_attempt`：最终被采用的稿次，不保证是最后一稿。
- `passed`：满足当前规则总分、押韵、结构和 Hook 硬门槛。
- `retrying`：当前稿未通过，仍有生成预算。
- `capped`：达到三稿上限仍未通过，采用历史最高规则分稿继续。
- `scores.rhyme`：押韵规则分。
- `scores.structure`：结构规则分。
- `scores.total`：70% 押韵 + 30% 结构；不是音乐质量分。

## 6. 开发过程中遇到的问题与解决办法

### 6.1 项目环境被其他 Python 环境污染

问题：宿主终端反复注入 Hermes 的 Python 3.11 `PYTHONPATH`，而 MusicAgent 使用 Python 3.10。错误加载其他环境中的二进制包会导致 NumPy 等模块崩溃。

定位：核对实际解释器、环境变量和二进制包来源，确认问题不是 MusicAgent venv 本身损坏。

解决：所有项目 Python 命令显式清除 `PYTHONPATH`，并固定使用 `D:\MusicAgent\.venv\Scripts\python.exe`。

结果：项目测试和脚本使用同一 Python 3.10 环境，避免跨版本二进制污染。

### 6.2 uv 缓存目录权限错误

问题：用户级 `uv.toml` 把缓存指向无权限的 `D:/Hermes/uv-cache`，导致 `uv pip list` 和依赖管理失败。

定位：检查 uv 可执行文件、环境变量、项目配置和用户配置，确认根因是缓存目录权限，不是 uv 损坏。

解决：在项目根目录增加 `uv.toml`，用项目级配置把缓存改为 `./tmp/uv-cache`，不修改其他项目的全局设置。

结果：`uv cache dir` 和 `uv pip list` 正常；即使 venv 没有内置 pip，也不影响统一使用 uv 管理依赖。

### 6.3 Torch 下载受 TLS、403 和代理影响

问题：部分 PyTorch 下载域名连接被中断，默认工具请求又可能被 Cloudflare 拒绝。

解决：使用浏览器 User-Agent 从官方主站下载 Windows cu124 wheel 到 `data/wheels/`，再通过 `uv pip install --find-links data/wheels --no-index` 本地安装。国内资源和外网资源按需区分代理，不全局修改代理。

结果：Torch 2.6.0+cu124、Torchaudio 和 CUDA 链路可用，安装文件留在 D 盘可复用。

### 6.4 DeepSeek 请求被无效代理拦截

问题：终端继承了 `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY=http://127.0.0.1:9`，真实请求在本机代理阶段失败，尚未到达 DeepSeek。

定位：检查代理环境变量和本地端口，再分别验证临时 Clash 7897 与直连。

解决：LLM 客户端使用 `trust_env=False`，默认直连；只有 `.env` 明确配置 `DEEPSEEK_PROXY_URL` 时才走项目代理。

结果：普通文本和 JSON 请求均已真实成功，项目不再依赖宿主终端的隐式代理状态。

### 6.5 DeepSeek JSON 偶发空内容或无效 JSON

问题：首次真实评估 6 个案例只有 1 个完成，4 个返回空内容，1 个不是有效 JSON。原实现只重试空内容，JSON 解析在重试循环外，坏 JSON 会直接终止。

解决：给三个 Agent 的系统提示加入 JSON 结构示例；把空内容、坏 JSON、根节点非对象和后续契约错误放入同一个有限重试循环；失败时保存不含正文和密钥的遥测。

结果：结构化失败可以在同一预算内纠正，也能通过 `operation`、请求次数、Token、`finish_reason` 和错误类型定位问题。

### 6.6 429 限流没有进入重试

问题：`RateLimitError` 是 `APIStatusError` 的子类。原捕获顺序先处理通用状态错误，导致 429 被立即抛出，配置的重试形同虚设。

解决：把 `RateLimitError` 捕获放到 `APIStatusError` 之前，继续使用有上限的指数退避。

结果：替身客户端回归测试确认 429 会进入有限重试；没有人为制造真实 429，因此不能声称线上限流已压测。

### 6.7 回炉作词连续耗尽 Token 但没有正文

问题：同一受控押韵案例连续 3 次空正文，累计 9,101 Token、70.714 秒。新增遥测显示三次都是 `finish_reason=length`，说明输出被 2,200 Token 上限截断。

解决：只对结构化 JSON 调用关闭 DeepSeek 思考模式，保持原 Token 上限；普通对话调用不覆盖模型默认思考配置。

结果：同一案例改为 1 次请求、3.384 秒、901 Token、`finish_reason=stop`，规则分 76.8 → 100.0。这个对照证明了结构化输出可用性和成本改善，不证明歌词审美提升。

### 6.8 JSON 语法正确但业务契约不合格

问题：`station-farewell` 返回了合法 JSON，但 Hook 没有原样出现在歌词正文，Pydantic 语义校验在调用结束后才失败，无法自动纠正。

解决：`chat_json()` 接受 `payload_validator`；字段、标签或 Hook 契约失败时抛出 `LLMContractError`，把最多三条脱敏字段错误追加到下一次请求，并与其他结构化失败共享同一总预算。

结果：离线测试覆盖“第一次 Hook 不合格、第二次纠正成功”；当前完整回归为 90/90。后续双作词真实试点中，结构型作词分支首次触发 `LLMContractError` 后自动修复成功，因此语义契约重试已有真实 API 路径证据。

### 6.9 用户指定时长被模型推断覆盖

问题：CLI 指定生成 30 秒，但需求 Agent 推断 180 秒，导致需求记录、歌词规划和实际音频时长不一致。

解决：把用户显式时长写入 LangGraph 状态，并在需求节点覆盖模型推断值，后续作词、质检、制作和音频统一使用该约束。

结果：真实图产物中的 `duration_seconds=30`，ffprobe 音频时长为 30.08 秒，语义一致。

### 6.10 HeartMuLa 加载阶段原生崩溃

问题：日志出现 `No module named 'triton'` 后，Python 在权重第 1/4 分片附近退出，容易误判为 Triton 缺失或 GPU OOM。

定位：对比曾成功的同一配置，检查权重完整性、进程身份、GPU 状态和 Windows `Resource-Exhaustion-Detector` 事件。事件 2004 明确记录虚拟内存不足；成功复验时系统提交峰值约 35.34 GB。

解决：先关闭 Water、Ollama 等大内存进程；Web 再次失败后，把 E 盘页面文件初始容量调到约 28 GB，使系统提交上限升到 43.19 GB。保留 `lazy_load=True`，没有盲目安装 Triton。

结果：相同代码完成 4/4 HeartMuLa 分片、375/375 采样和 2/2 HeartCodec 解码，生成 30.08 秒 MP3。`No module named 'triton'` 仍出现但不阻塞成功，证明它不是此前失败的必要原因。

### 6.11 GPU 原生失败可能带走 Web 服务

问题：HeartMuLa 加载慢、内存压力高，并可能出现原生进程退出；如果直接在 Web 进程内加载，失败会影响 API 和已生成文本。

解决：把音频放到独立 Python 子进程中；Web 进程只管理任务状态和日志。音频任务单容量、30 分钟超时、不做隐式 GPU 重试。

结果：两次音频加载失败时 Web 服务仍正常，歌词、79.7 分质检报告和制作方案保持可见，用户可以手动重试；扩容后第三次生成成功。

### 6.12 服务重启后历史作品消失

问题：文本任务只存在内存任务表中。真实任务虽然已经写入 `task.json`，服务重启后首页仍只显示静态样例。

解决：列表和详情接口扫描 `data/output/web/`，只读取目录名、任务 ID 和状态都通过校验的 `done/failed` 快照。

结果：重启后真实作品重新出现在历史列表。这个能力只用于终态查看，不恢复 `pending/running` 工作，也不属于断点续跑。

### 6.13 规则通过容易被误说成质量提升

问题：系统会选择历史规则分最高稿，天然造成终稿分数不低于初稿；规则分本身也不衡量自然度和听感。如果只展示分数，容易得出错误因果结论。

解决：把自然主题和受控缺陷分开评估；分别记录回炉触发率、上限比例、指定缺陷检测/消失、Token 和延迟；生成匿名 A/B 材料，由人工评价自然度、主题贴合和 Hook。

结果：三类受控缺陷检测和指定修复为 3/3。三个自然主题盲评中，规则都选择意象型，人工选择意象型 1 次、结构型 2 次，胜者一致率 1/3。人工指出的关键问题是主题越界、情绪失控、叙事与意象不统一，均不属于当前规则分直接覆盖范围；因此不能泛化为“系统让歌词普遍更好听”。

### 6.14 双作词选优后，规则回炉链路提前结束

问题：接入匿名评审后，新主题真实运行能够完成选优，但入选稿规则首检不通过时，图只执行了一次作词改写，随后没有再次进入质检和制作；验证脚本最终缺少 `production_plan`。

根因：双作词初始路径是 `lyric_candidate → subjective_judge → select_lyricist → quality`，而旧的 `lyricist → quality` 回边只在单作词分支注册。`quality` 虽然正确路由回了入选 persona，改写节点却没有后继边，因此图正常但过早结束。

解决：把 `lyricist → quality` 改为单双作词共用的回边，并新增“主观胜者规则不通过、连续改写到三稿后仍能进入制作”的回归测试。真实同题重跑后，首轮规则分 55.3，第二稿 93.0 通过并完成制作。这个案例说明节点能够单独运行不等于循环控制流完整，必须用真实会触发分支的样本验证。

## 7. 为什么采用这些方案

### 为什么先做单作词人闭环

单作词人已经足以验证结构化输出、规则检测、反馈回炉、预算上限和版本选择。如果在这条链路还不稳定时直接上双作词人和 RAG，会同时引入更多变量，问题难以归因。

### 为什么质检用规则而不是再调用 LLM

十三辙归类、结构标签、行数和 Hook 位置可以确定性判断。规则结果可重复、可解释、便宜，还能给出精确行号。独立 LLM 评审只补足主题、自然度、情绪和意象比较，不替代这些硬检查；职责分层后，主观高分也不能绕过规则下限。

### 为什么文本和音频分开

文本链路通常是秒级到几十秒级，音频单个 30 秒样本约需 5～6 分钟并占用很高系统提交量。分开后可以快速调试 Agent 和质检，也能在 GPU 失败时保住文本结果。

### 为什么限制并发和重试

本机只有一张 RTX 4060 8GB，文本 API 也存在 Token 和限流成本。文本采用一个运行、两个等待；音频只允许一个任务；每个结构化 LLM 调用最多三次 API 尝试；歌词最多三稿。这些限制让成本、内存和死循环风险可控。

### 为什么保存逐轮产物

最终歌词不能说明系统为什么选择它，也不能证明回炉发生过。保存每稿、分数、反馈、Token、耗时和失败摘要后，才有可复现的演示证据和排错依据。
