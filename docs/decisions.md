# 技术决策记录

## D1-001｜本地 4060 作为开发与预生成后端

- 日期：2026-09-04
- 状态：已决定

### 决策

现阶段继续使用本机 RTX 4060 开发和验证 HeartMuLa，不购买服务器，也不立即租用云 GPU。

本地生成服务按以下方式使用：

- 开发阶段：生成短试听，验证歌词、tags 和音频链路
- 演示阶段：使用已生成并保存的真实成品及工作流记录
- 产品结构：保留统一的音频生成接口，为后续接入云 GPU 或 Suno 留出切换点

### 依据

- 30 秒音频耗时 305.1 秒，60 秒音频耗时 532.4 秒，当前不适合现场等待完整歌曲生成
- 模型已经在 4060 上成功运行，继续本地开发不需要新增费用
- 项目核心亮点是多 Agent、歌词质检、回炉控制和可观测性，不应被音频生成硬件成本阻塞
- 当前没有并发用户和批量生成需求，购买或长期租用服务器的投入产出比不足

### 触发重新评估的条件

满足以下任一条件时，重新评估云 GPU：

- 面试演示必须现场生成完整歌曲
- 需要多人同时试用
- 需要批量生成音频进行评测
- 本地短试听也无法满足交互体验

### 实施约束

- 音频生成必须是可替换的服务接口，不把 HeartMuLa 细节散落在 Agent 节点中
- 完整生成采用异步任务，不能阻塞 Web 请求
- 保存音频、歌词、tags、质检结果和生成日志，保证演示结果可追溯
- 不把预生成成品伪装成刚刚完成的实时生成

## D2-002｜DeepSeek 默认直连，代理作为回退

- 日期：2026-09-04
- 状态：已决定

### 决策

MusicAgent 默认直接访问 `https://api.deepseek.com`。只有直连失败时，才在 `.env` 中显式配置 `DEEPSEEK_PROXY_URL=http://127.0.0.1:7897` 使用 Clash Verge 的混合代理端口。

### 依据

- 在终端仍携带无效代理 `127.0.0.1:9` 的条件下，项目 LLM 客户端通过 `trust_env=False` 成功直连 DeepSeek。
- 直连链路更短，不依赖 Clash 是否启动、端口是否变化或代理节点可用性。
- 本机运行的 Python 服务与 Codex 云端模型服务是不同网络进程；不应因 Codex 使用代理就强制业务 API 也走代理。

### 回退方式

若直连失败，在 `.env` 增加：

```env
DEEPSEEK_PROXY_URL=http://127.0.0.1:7897
```

LLM 封装只读取这个显式项目配置，不继承终端的 `HTTP_PROXY`、`HTTPS_PROXY` 或 `ALL_PROXY`。

## D6-003｜歌词质检 v1 使用规则门槛与有限回炉

- 日期：2026-09-08
- 状态：已决定并实现

### 决策

歌词质检 v1 只使用确定性规则：`pypinyin` 提取行尾韵母并映射十三辙，结合段落结构检查输出可定位的问题和改写建议。总分由押韵 70% 与结构 30% 构成；总分至少 75、押韵至少 70、且 Hook 必须原样出现在副歌或 Hook 段，才判定通过。

LangGraph 中初稿计为第 1 次作词；不通过时将结构化规则反馈交回作词 Agent，最多生成 3 版。达到上限仍未通过时，选择三版中规则分最高的版本继续后续制作和音频生成，并标记为 `capped`，不能伪装成质检通过。

### 依据

- 十三辙和段落标签可由可复现规则判断，适合在不调用 LLM 的情况下给出行号、韵母、辙口和修改方向。
- `pypinyin` 的严格韵母模式会保留 `ü`、`iou/uei/uen` 等标准韵母信息，避免因为拼写缩略导致十三辙误分类。
- 30 秒试听只有两三行段落；结构最低行数按时长分级，避免直接套用完整歌曲的长段落标准。
- 音频生成成本高且本机内存压力大，歌词回炉必须发生在制作和音频生成之前；上限与 `capped` 状态防止死循环和错误成功标记。

### 限制

- 规则分只表示韵脚与结构合规，不表示歌词自然度、主题贴合、旋律可唱性或音频听感。
- 响亮辙仅是最高 10 分的小幅项目规则加权，尚未通过人工听评证明能提升听感。
- 平仄节奏、主题一致性、候选押韵词检索和双作词人 PK 属于后续 W2，不在 D6-D7 声称完成。

## D7-004｜文本工作流验证与音频生成解耦

- 日期：2026-09-08
- 状态：已决定并实现

### 决策

提供 `scripts.run_text_workflow_validation`：复用真实 DeepSeek、LangGraph、规则质检、回炉和制作 Agent，但用明确的 `audio_skipped.json` 代替 HeartMuLa 调用。每次运行保存需求、最终歌词、制作方案、`quality_report.json` 与 `lyric_revision_history.json`。

### 依据

- 歌词规则、回炉控制和 LLM 协作的验证不依赖 GPU；本机 HeartMuLa 生成慢且有较高虚拟内存压力。
- 质检的项目价值需要可追溯的“候选歌词 → 分数 → 反馈 → 最终选择”证据，而不是只有终版歌词或控制台日志。
- `capped` 状态下仍可按最高分草稿继续后续链路，但必须写入报告并在 CLI 明确提示，不能把未通过质检的音频当作正常通过结果。

### 边界

- 文本验证的 `audio_skipped.json` 明确标记 `audio_generated: false`；它不能作为新的音频生成成功证据。
- 真实文本首稿通过只证明真实集成可用；不证明回炉一定提高自然度，后续需要固定主题的基线对照与人工评价。

## D7-005｜回炉评估采用自然主题与受控缺陷双轨证据

- 日期：2026-09-08
- 状态：已决定并实现评估工具，尚未执行真实试点

### 决策

评估歌词回炉时，将三条自然主题工作流与三条确定性受控缺陷分开运行和报告。自然主题记录首稿、回炉记录、最终选择、DeepSeek Token 与延迟；受控缺陷分别覆盖目标韵脚失配、Hook 未进入副歌、段落长度不足，验证反馈能否在最多三版内被修复。两类结果都生成匿名 A/B 人工评分材料，但不将规则分提升直接表述为自然度提升。

总结文件必须单独输出自然主题的回炉触发率和上限比例，以及受控缺陷的检测率、指定缺陷修复率、整体规则通过数。指定缺陷是否修复以该缺陷代码是否从选中版本的报告中消失为准，不能用整体 `passed` 状态代替。若某个案例失败，保存其 `failure.json` 并继续其他案例；失败案例单列，不并入成功率分母。

回炉作词提示必须携带上一版歌词和具体规则反馈，要求保留未被要求修改的内容、主题与可用意象，避免把“基于反馈重新生成”错误描述成“修改原稿”。

### 依据

- 此前真实文本验证的首稿即以 100 分通过，不能据此证明真实模型在收到反馈后有修复能力。
- 工作流会选择历史最高规则分版本，因此终版规则分不低于初稿具有程序选择效应，不能作为独立的能力增益证据。
- 原实现的回炉提示没有上一版歌词；`chat_json()` 也没有保留调用用量，无法复核修改保真度或评估成本。
- 规则分不衡量自然度、主题贴合、可唱性或音频听感，需要与盲评结果分开解释。

### 边界

- 试点只有 3 个自然主题和 3 个受控缺陷，属于工程验证，不具备统计显著性。
- 受控缺陷验证的是规则修复能力，不代表自然题材中一定会触发或改善回炉。
- 评估脚本必须显式传入 `--execute` 才调用 DeepSeek，并始终写入 `audio_generated: false`，不加载 HeartMuLa 或 GPU。
- 实验配置记录模型、超时、重试上限和三个 Agent 的温度/Token 上限；盲评材料提供主题、情绪、曲风，但不提供初稿/终稿身份或受控缺陷类型。

## WEB-001｜文本任务与音频解耦，采用单进程有界执行

- 日期：2026-09-08；依据：已确认的前端 MVP 第 3 步。
- 使用明确的 text_only 图编译选项，制作节点后结束；保留旧音频图默认行为，不构造 GPU 服务或以跳过标记冒充音频。
- 本地演示采用一个执行线程、两个等待名额，满载返回 429；由 FastAPI lifespan 启动/关闭执行器。前端约 1.2 秒轮询，终态后停止，断线退避且禁止重复提交。
- 阶段由节点实际执行事件驱动；task.json 原子替换保存进度，文本完成后另存需求/歌词/草稿/制作与质检文件。成功/失败持久化后发布终态；保存异常仍向内存任务报告失败。
- 服务重启会丢失运行中任务的内存状态；API 会读取严格校验过的 `done/failed` task.json 供历史查看，不恢复 `pending/running` 执行、不支持任务续跑。只运行一个 worker。
- 格式校验失败不放宽既有契约、不隐式重复调用；本地 failure.json 只保存错误类型和字段位置，不保存密钥、提示词或模型原始输入。首个真实失败发生在增加字段诊断之前，无法据当时记录确认具体字段。
- 技术参考：FastAPI 官方 https://fastapi.tiangolo.com/advanced/events/ 与 https://fastapi.tiangolo.com/tutorial/static-files/ 。

## WEB-002｜按需音频使用独立、单容量子进程任务

- 日期：2026-09-08
- 状态：已实现并完成真实 Web MP3 验收

### 决策

文本任务完成后，前端显式调用 `POST /api/tasks/{task_id}/audio`。服务端只读取该任务落盘的最终采用歌词和制作 tags，不重复调用 DeepSeek。HeartMuLa 在独立 Python 子进程中执行；音频侧只接受一个运行任务，不设置隐式 GPU 重试。只有预期目录中的非空 MP3 通过校验后才发布播放 URL。

音频任务把 pending/running/done/failed、采用稿次、规则状态、时间、文件大小和错误摘要保存到源文本任务目录。音频失败不改变文本任务的 done 状态，页面保留歌词、质检和制作结果，并提供人工重试；服务重启时旧运行态会转为可重试的失败态。

### 依据与限制

- HeartMuLa 曾出现原生进程崩溃；子进程隔离能保住 Web 服务及已经完成的文本产物。
- 本地 RTX 4060 只有 8 GB 显存，且既有 30 秒成功复验的系统提交峰值约为 35.34 GB，因此不允许并发 GPU 生成。
- 2026-09-08 对《晚风陪我回家》的两次 Web 生成均在 checkpoint 第 1 分片加载阶段失败；Windows 事件 2004 明确记录虚拟内存不足。当时提交量约 20.15/30.69 GB，不能把这次失败归因于 Triton 缺失。
- 将 E 盘页面文件初始容量调整为 28 GB 后，系统提交上限为 43.19 GB、空闲显存约 6.5 GB。相同文本任务第三次执行完成 375 步采样和 codec 解码，生成 30.08 秒、558,624 字节 MP3；服务接口返回 200 `audio/mpeg`，浏览器播放器完成播放/暂停验收。
- 当前实现只承诺把歌词和 tags 交给模型，不宣称 BPM、完整制作说明或指定音色会被严格执行。

## D2-006｜结构化输出采用单一有限重试预算、契约修复与脱敏失败遥测

- 日期：2026-09-08
- 状态：已实现；已完成一条受控缺陷真实 API 冒烟验证，尚未完成完整试点

### 决策

DeepSeek Chat Completions 的 JSON 输出继续使用既有 `response_format={"type":"json_object"}`。三个结构化 Agent 的系统提示均加入 JSON 对象示例；空内容、无效 JSON、JSON 根节点非对象，以及 Agent 的 Pydantic/领域输出契约失败，均纳入同一个 `LLM_MAX_RETRIES` 总预算，而不是各自嵌套重试。

每个逻辑调用保存不含提示词、响应正文或密钥的遥测：Agent 阶段、成功/失败、实际 API 次数、累计 Token、缺失用量次数、最后 `finish_reason`、最后内容长度、错误类型和重试原因。评估案例失败时，将该案例截至失败前的遥测写入 `failure.json`。

### 依据

- 首次真实试点中，4 个案例为空内容、1 个案例为非有效 JSON；原实现在空内容时会重试，但 `json.loads()` 位于重试循环外，格式错误会直接终止案例。
- DeepSeek 官方 JSON Output 文档要求提示中明确 JSON，并建议提供示例和合理控制输出长度；当前三个 Agent 原本已经分别使用 800 / 2200 / 1000 的 `max_tokens`，因此本次不重复调整这一参数。
- 嵌套两层各三次重试可能将单次逻辑调用放大为九次收费请求，不符合歌词回炉的预算上限。

### 边界

- 最初曾暂不关闭 DeepSeek 默认思考模式；后续 `finish_reason=length` 证据出现后，已在下方“首次冒烟与后续决策”中改为仅关闭结构化 JSON 调用的思考模式。普通 `chat()` 仍不覆盖模型默认行为。
- 遥测只用于定位可靠性和成本，不保存模型原文，因此无法替代人工歌词审阅。

### 首次冒烟与后续决策（2026-09-08）

- 仅运行受控案例 `rhyme-mismatch` 后，`lyricist_rewrite` 连续 3 次返回空正文；失败记录显示每次均以 `finish_reason=length` 截断，累计 completion Token 为 6,599，接近 `3 × 2,200` 上限。
- 这证明当前回炉作词在既有 Token 上限下被截断，不能再将其归为无证据的偶发空响应。DeepSeek 默认启用高强度思考模式是合理的待验证解释，但遥测不保存 reasoning 正文，因此不能据此断言所有 Token 都被思考内容占用。
- 用户选择为结构化 JSON 调用关闭思考模式、保留既有 Token 上限；普通 `chat()` 不传此覆盖，保持模型默认行为。配置默认值为 `LLM_JSON_DISABLE_THINKING=true`，可在 `.env` 显式改为 `false` 做后续对照。
- 同一 `rhyme-mismatch` 受控案例在新配置下 1 次 `lyricist_rewrite` 成功完成：3.384 秒、901 Token、`finish_reason=stop`；规则分从 76.8 提升到 100.0，指定 `rhyme_pattern_mismatch` 消失且无新增规则问题。此前同一案例为 3 次请求、70.714 秒、9,101 Token 后失败。该对照证明配置解决了该受控场景的截断问题，不证明自然歌词质量或其余案例同样改善。
- 继续运行的 `hook-outside-chorus` 与 `short-verse` 也各在一次改写后通过：前者 3.522 秒、652 Token，指定 `missing_hook` 消失；后者在一次 `APIConnectionError` 后按同一总重试预算恢复，9.900 秒、701 Token，指定 `short_section` 与伴随的 `missing_section` 均消失。至此三条预设受控缺陷的检测和修复均为 3/3；自然主题、人工盲评仍是独立未验证项。
- 三条自然主题在关闭思考模式后有两条完整首稿通过：`summer-night-home` 为 90.1 分、7.334 秒、1,498 Token，`old-town-reunion` 为 95.9 分、7.665 秒、1,581 Token，均未触发回炉。`station-farewell` 的需求与作词 JSON 请求均成功，但 Hook 未原样出现在歌词正文，`LyricDraft` 语义校验失败。该失败证明 JSON 解析重试不足以保证 Agent 输出契约；是否将 Pydantic/领域校验纳入同一有限重试预算，需要单独设计，不能把本次 2/3 首稿通过报告为自然回炉效果。
- 为修复该缺口，调用层允许每个 Agent 传入其 Pydantic 模型的脱敏校验器。有效 JSON 若未通过字段、段落标签或 Hook 等契约，调用层把最多三条字段级错误追加到下一次请求，要求只返回修正后的 JSON；它与空内容、坏 JSON 共享同一总预算。不会保存或回传模型原始正文。
- 56 项离线回归通过，其中包含“Hook 未进入正文 → `LLMContractError` → 下一次请求带具体反馈并成功”的无网络测试。随后仅重跑此前失败的 `station-farewell`：完整首稿通过，10.254 秒、1,533 Token，3 个 JSON 调用均为一次 `finish_reason=stop`。本次输出首稿已合格，因此证明的是该案例恢复完成，不是语义重试路径已被真实 API 触发的证明。

## D8-007｜双作词人并行生成，先采用确定性规则初筛

- 日期：2026-09-09
- 状态：D8.1-D8.2 已实现；D8.3 部分实现

### 决策

首次作词由两个固定 persona 接收同一份 `SongRequirement`：A 优先押韵和结构，B 优先具体意象与叙事。LangGraph 使用 `Send` 并行执行两个分支；每份候选立即运行同一套纯规则质检。初筛依次比较：是否通过硬性规则、规则总分、押韵分、结构分；全部相同时固定优先 A，保证结果可复现。

初筛选中的 persona 继续承担该歌词的规则回炉，最多三版的原有预算不变。制作和音频阶段只消费最终采用稿。两份候选、规则报告、选择方法及选择理由分别保存，规则分不得描述为自然度或听感分。

### 依据与验证

- 双 persona 的目标是形成可比较的自然候选，而不是将人为缺陷修复稿包装成自然 A/B。
- 共享 `DeepSeekLLM` 的客户端首次初始化增加互斥锁；Web 进度事件与快照写入也串行化，避免两个并行分支竞争初始化或覆盖任务记录。
- 完整离线回归 60/60 通过；线程屏障测试只有两个作词分支同时进入才能完成，证明执行路径实际并发。

## D8-011｜匿名主观评审与确定性规则分层组合

- 日期：2026-09-09
- 状态：已实现并完成真实文本验证

### 决策

在双作词候选之后增加独立 `LyricJudgeAgent`。评审只读取结构化歌曲需求与匿名 A/B 的标题、Hook 和歌词正文，不读取 persona 身份、规则分或旧的规则胜者。五个主观维度及权重固定为：主题契合 25%、自然度 20%、情绪控制 20%、叙事与意象一致性 20%、Hook 记忆点 15%；LLM 只输出 1～5 分、歌词证据、理由和结构化问题，0～100 加权总分由程序计算。

最终选择顺序固定为：单方重大主题问题先淘汰；两版均无重大主题问题时，主观分差达到 3 分选择高分版，分差不足 3 分才依次比较规则是否通过、规则总分、押韵分、结构分和稳定 persona 顺序。双方均有重大主题问题时，两位作词人分别接收自己的证据化反馈并共同回炉，最多 1 次；第二轮仍有重大问题则标记 `regeneration_exhausted` 并按上述有限选择继续，不形成死循环。选中创意底稿后仍进入原有最多三稿的确定性规则回炉，D8 不做音频评审。

### 依据与验证

- 三条人工盲评证明规则分不能覆盖“带我去远方”的叙事方向、“风霜酿糖”的意象转换和“隔阴阳”的情绪越界，因此需要独立主观层；同时只有三例和一名评审者，不足以取消规则或训练固定 persona 偏好。

- 完整离线回归 74/74 通过，覆盖匿名输入、程序加权、0.5 分档、单方重大问题淘汰、近分规则决胜、双方共同回炉一次、回炉上限和评审后规则改写回边。

### 边界

- 2/3 只是本轮三条固定歌词与一名人工评审者的描述性一致性，不能外推成模型准确率或自然歌词质量提升。

- 规则权重、规则通过阈值和入选后最多三稿的上限均未改变；RAG、平仄/主题规则检查器和音频评审仍未实现。
